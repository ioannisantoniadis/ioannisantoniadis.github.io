A preregistered study · October–November 2026

Does an AI agent pick the first tool it sees?

Agents increasingly choose from tool lists that another system has ranked, such as a tool-search result. If their choices bend to position the way search users' clicks do, you could fit a curve once and correct for it. We tested that idea on three language models and 26,820 paid calls.

The question

A search engine habit, applied to agents

In web search, people click higher results more often, partly because they look at them first. Click models estimate that examination curve, and learning-to-rank systems use it to correct logged clicks. A harness that shows an agent a ranked list of tools (a tool-search result, a registry, a retriever's top 20) sits where the search engine sits. Agents are known to be sensitive to the order and wording of options, so the question is whether the toolkit carries over.

The first step it needs is a position curve that is stable: fitted on one kind of task, it should predict choices on another. We tested that step directly, with two preregistered hypotheses:

H1A position curve fitted on one task family predicts choices on anotherfails its preregistered test: no curve found to transfer

The setup

One trial, one tool call

Tools come from BiasBusters, a published benchmark built on ToolBench's collection of real web APIs. It groups them into families of five equivalent tools; each family comes with 100 queries that every tool in it can answer. Three families were used: c4 (IP geolocation), c3 (news headlines) and c10 (weather forecasts). Each trial is a single chat request: a fixed system prompt, one query, and K tools passed as function definitions in list order, with K = 5 or 20. A response counts only if it calls exactly one listed tool.

The rest of the list is distractors. Near-misses look relevant but can't do the job; they were mined by text similarity and checked one by one by hand. In the hard tier every distractor is a near-miss; in the 50% tier half are swapped for unrelated tools. Descriptions were rewritten by a fixed rule (promotional words removed, at most 30 words), and every tool got the same empty parameter schema, so only the choice of tool is scored and only names, descriptions and position differ.

Choices are fitted with a conditional logit: each tool's appeal is a capability term plus a position term β, with position 1 fixed at zero. A positive β means that slot draws more choices than slot 1. A curve counts as positional when a likelihood-ratio test beats the same model without position terms, at a significance level divided by the number of tests (0.05/8 in E1).

Each stage had a decision rule written down before its first paid call, including a stop rule: if no model shows a positional curve that predicts better than no position effect at all, write up and stop.

Three experiments, each with its decision rule fixed before the first call

From ceiling to null

E0 · pilot · family c4

One capable tool per list

Haiku 5.5, Sonnet 5.5 and Qwen3.5-9B, with the capable tool placed in every slot for every query.

Result: 0 wrong-tool choices in 3,900 trials. When one tool fits, models find it anywhere in a list of 20, so position can't show.

E0b · harder variant · family c4

Two equally capable tools

Tool A in the slot under test, tool B at a random other slot, near-misses around them. Now position can decide between equals.

Result: position found for Sonnet 5.5 and Qwen3.5-9B at K = 20 (p = 3.6 × 10⁻¹² and 3.5 × 10⁻¹⁴). Still 0 of 3,841 choices went to a near-miss.

E1 · minimal experiment · families c3, c10

Does the curve transfer?

Haiku 5.5 and Qwen3.5-9B, two new families, both tiers, 9,360 calls per model. Fit the curve on one family, predict the other.

Result: no positional curve in any of the 8 model × condition cells (smallest p = 0.009, against a bar of 0.006), so there was no curve to transfer. The stop rule ended the study.

What it means

Position tips ties; it doesn't break tools

Strictly, E1 is a non-detection: on two new families no model showed a position curve the tests could tell from none, so H1 and H1b fail under the preregistered rules before any transfer could count. Small effects remain possible. In 6 of the 8 E1 cells the earlier of two capable tools was taken slightly more than half the time (53–54%), a primacy of a few points that the per-slot tests weren't built to detect. A simpler one-parameter decay curve might have transferred where the per-slot curve couldn't; that wasn't tested.

For tool lists like these, a per-model position curve isn't something you can estimate once and carry around. When one tool fits, models find it wherever it sits. When several fit, position can tip the choice, strongly for some model and family pairs and barely at all for others, and the curve's shape changes with the family. In 6 of the 8 E1 cells the two families' curves differed significantly at some slot, so pooling may also hide effects of opposite sign.

The practical upshot is modest. Position here changes which of several adequate tools gets used, not whether the job gets done. That makes it more a fairness question for tool providers than a reliability question for users. That reading is ours; the study didn't test it.

Limits worth knowing. E1 tested Haiku 5.5 and Qwen3.5-9B; Sonnet 5.5, the model with the clearest E0b effect, was deferred to keep costs low, and the stop rule ended the study first. The E0b effect comes from one family and can't be re-checked from raw logs, which weren't kept. Descriptions were normalised and schemas emptied, so the near-perfect accuracy may partly reflect these clean lists. Calls were single-turn with at most 20 tools, and the near-misses were checked by one person.

How it was run

Agents did the work; a person held the gates

The idea came from an idea garden, a pipeline that proposes and critiques research ideas. A scheduled Claude Code agent then ran the project daily: it completed the preregistration, wrote all 6,927 lines of code with 152 tests, ran every experiment and drafted the paper. Anything that cost money or changed a decision rule went to a person as a gate: a written request with its cost worked out, which only the person could approve.

The agents

  • Made 118 of the 137 commits; 64 of those were automatic checkpoints and run logs.
  • Wrote every gate request, each with a recommended spending limit and cheaper options.
  • Proposed each redesign after a result, and checked its decision rule on simulated agents before any paid call.
  • Never approved its own request; every paid run enforced its limit in code.

The person

  • Set the rules: preregister first, results only from code, a gate for anything that costs money.
  • Decided all 10 gates, 7 of them the day they were asked.
  • Hand-checked all 90 near-miss tools.
  • Cut E1 to two cheap models, set the stop rule in advance, and added the rule "cheapest informative step first".

Where the agents went wrong

  1. A model id that didn't exist. Caught when the key was checked; the agent then added a free check of ids, providers and prices before any paid call.
  2. A preregistered step nearly skipped. The second-model capability check wasn't built until the agent noticed it had to run before E0. Caught before any paid call.
  3. A pilot that was too easy. E0 followed the plan, but models were at ceiling, so position couldn't show. The agent proposed E0b, and found on synthetic agents that E0's rule would misjudge it.
  4. Raw call logs lost. E0 and E0b's per-call logs lived only in their containers. From E1 on, every paid log was saved to the repository as the run went.
  5. Designs sized for the full plan. The agent kept planning E1 for four models. The person cut it to two; E1 cost $4.39 of its $10 limit and reached the stop rule.
